# 깃헙 정리 규칙

이 저장소의 README는 데이터 분석 흐름(질문 → 데이터 → 방법 → 결과 → 한계) 순서로, 커밋은 `[종류/범위] 한 일` 한 줄로, 주석은 코드가 왜 그렇게 짜였는지만 짧게 적는다. 이 세 가지를 지키면 몇 달 뒤 저장소를 열어도 README 상단, 커밋 목록, 주석만으로 각 작업을 다시 파악할 수 있다.

참고 자료: GitHub 활용 취업용 포트폴리오 PDF(데이터 직무 README 순서, Conventional Commits, STAR 트러블슈팅, Trade-off 표), [production-ai-performance-lab](https://github.com/Lee-jun-young98/production-ai-performance-lab) 저장소(한글 문서, README는 목차 역할, 실험별 문서 분리).

### 작성 요령

- 결과는 "잘 됐다" 대신 숫자로 쓴다. 아직 수치가 없으면 측정 기준과 다음 검증 계획을 쓴다.
- 방법을 고른 이유는 Trade-off 표 한 개로 정리한다: 선택한 방법, 비교한 대안, 고른 이유, 포기한 점.
- 데이터 흐름은 Mermaid 그림 한 장으로 그리고, 그림 아래에 해석 한 문장을 붙인다.
- 막혔던 문제는 STAR(상황, 해야 할 일, 한 일, 결과)로 짧게 남긴다. 오타 수정 같은 건 넣지 않는다.
- 명령어는 코드 블록, 비교는 표, 절차는 번호 목록으로 쓴다.

## 규칙 2. 커밋 메시지

커밋 제목은 `[종류/범위] 한 일` 형식으로, 종류와 범위도 한글로 쓴다. 커밋 하나에는 한 가지 작업만 담는다. Conventional Commits의 구조(종류 + 범위 + 내용)는 그대로 두고 말만 한글로 바꿨다.

```text
[기능/전처리] 결측 구간 선형 보간 추가

- 5분 이하 결측만 보간, 그 이상은 구간 제외
- 3월 센서 교체 기간(3/12~3/15) 데이터 제외
```

- 제목은 50자 안쪽, 끝에 마침표 없이 "~추가", "~수정"처럼 명사로 끝낸다.
- 범위가 딱히 없으면 `[문서] README 실행 방법 추가`처럼 종류만 쓴다.
- 본문은 필요할 때만 쓴다. 무엇을 바꿨는지보다 왜 바꿨는지, 어떤 기준을 정했는지를 적는다.
- 분석 결과가 바뀐 커밋은 본문에 수치를 남긴다. (예: `F1 0.71 → 0.78`)
- `Co-Authored-By: Claude ...`, `Claude-Session: ...` 같은 AI 도구 표시 줄은 넣지 않는다. Claude로 작업한 커밋도 작성자는 저장소 주인 한 명으로 남긴다.

### 종류

| 종류 | 언제 쓰나 | 예시 |
| --- | --- | --- |
| 기능 | 새 기능, 새 분석 단계 추가 | `[기능/모델] LSTM 기반 이상 탐지 모델 추가` |
| 수정 | 잘못된 결과나 에러 수정 | `[수정/전처리] 타임스탬프 시간대 오류 수정` |
| 실험 | 실험, 파라미터 비교 (결과는 본문에 숫자로) | `[실험/모델] 윈도우 크기 30/60/120 비교` |
| 정리 | 결과는 그대로이고 코드 구조만 변경 | `[정리/EDA] 그래프 함수 하나로 합침` |
| 문서 | README, 문서, 주석 | `[문서] 데이터 전처리 기준 README에 정리` |
| 데이터 | 데이터 추가, 교체, 샘플 갱신 | `[데이터] 2024년 2분기 센서 데이터 샘플 추가` |
| 설정 | 환경 설정, 패키지, .gitignore | `[설정] requirements.txt 버전 고정` |

### 범위

분석 단계 이름을 쓴다: `전처리`, `EDA`, `특징`, `모델`, `시각화`, `논문`. 더 늘리지 않는 것이 좋다.

### 알아보기 어려운 커밋 고치기

| 나쁜 예 | 좋은 예 |
| --- | --- |
| `update` | `[문서] 실행 방법과 폴더 구조 README에 추가` |
| `수정` | `[수정/EDA] 설비별 평균 계산에서 주말 데이터 누락 수정` |
| `최종`, `최종진짜` | `[실험/모델] 최종 모델 RandomForest로 확정 (F1 0.82)` |
| `코드 업로드` (파일 30개 한 번에) | 작업 단위로 나눠서 여러 번 커밋 |

완성된 작업 단위(예: 전처리 완료, 모델 1차 비교 완료)마다 README의 작업 기록 표에 한 줄을 추가하고 관련 커밋을 적어두면, 커밋 목록과 README가 서로 이어진다.

## 규칙 3. 코드 주석

주석은 코드만 봐서는 알 수 없는 것, 즉 왜 그렇게 했는지와 그 숫자가 어디서 왔는지만 쓴다. 코드를 한 줄씩 따라 읽는 주석과 길고 정중한 문장이 AI가 쓴 티가 가장 많이 나는 부분이다.

### 쓸 것

- **파일 맨 위 2~3줄**: 이 파일이 하는 일, 입력과 출력 파일.
- **기준값의 근거**: 임계값, 윈도우 크기, 제외 기간 같은 숫자가 어디서 나왔는지. (설비 매뉴얼, EDA 결과, 교수님 피드백 등)
- **데이터 사정**: 단위(kW, A, V), 샘플링 주기, 센서 교체나 점검으로 값이 튀는 구간.
- **다른 방법을 안 쓴 이유**: 해봤는데 안 됐던 것. 나중에 같은 시행착오를 막아준다.
- **TODO**: 날짜와 함께. 예: `# TODO(10/12): 설비 B도 같은 기준으로 확인`

### 쓰지 않을 것

- 코드를 그대로 다시 말하는 주석. (`# 데이터프레임을 불러옵니다`, `# 반복문을 돌며 처리합니다`)
- 모든 줄에 주석 달기, 모든 함수에 Args/Returns를 꽉 채운 docstring 달기.
- `# ===== Step 1: 데이터 로드 =====` 같은 장식선과 번호 매기기, 이모지.
- "효율적으로", "체계적으로", "강력한", "원활하게" 같은 꾸밈말.
- "~를 수행합니다", "~하는 역할을 합니다" 같은 존댓말 설명문.
- 수정 이력(`# 10/10 수정함`). 이력은 커밋에 남긴다.

### 문체

- 짧게 끊어 쓴다: "~함", "~용", "~기준", 또는 명사로 끝내기. 한 주석은 대부분 한 줄.
- 조건과 문제를 같이 적을 때는 "~할 경우, ~하는 문제 있음" 형태로 쓴다.
- 변수명, 함수명은 영어, 주석은 한글로 통일한다.
- 모든 함수에 달지 않는다. 이름만 봐도 알면 생략하고, 헷갈리는 곳에만 단다. 그래서 주석 개수가 파일마다 다르고, 그게 자연스럽다.
- 자기가 겪은 일을 그대로 쓴다: "3월 데이터를 포함할 경우, 평균이 튀는 문제 있어 제외", "대학 서버에서 한 번에 읽을 경우, 메모리 부족 문제 있어 나눠서 읽음".

### 예시

AI 티가 나는 주석:

```python
# ========== Step 2: 데이터 전처리 ==========
def remove_outliers(df, col):
    """
    주어진 데이터프레임에서 이상치를 효과적으로 제거하는 함수입니다.

    Args:
        df (pd.DataFrame): 입력 데이터프레임
        col (str): 대상 컬럼
    Returns:
        pd.DataFrame: 이상치가 제거된 데이터프레임
    """
    # 1사분위수를 계산합니다
    q1 = df[col].quantile(0.25)
    # 3사분위수를 계산합니다
    q3 = df[col].quantile(0.75)
    # IQR을 계산합니다
    iqr = q3 - q1
    # 이상치를 필터링하여 반환합니다
    return df[(df[col] >= q1 - 1.5 * iqr) & (df[col] <= q3 + 1.5 * iqr)]
```

사람이 쓴 것 같은 주석:

```python
def remove_outliers(df, col):
    # IQR 1.5배 기준. 3배로 했을 경우, 기동 직후 돌입전류가 안 걸러지는 문제 있음
    q1, q3 = df[col].quantile([0.25, 0.75])
    iqr = q3 - q1
    return df[df[col].between(q1 - 1.5 * iqr, q3 + 1.5 * iqr)]
```

### 푸시 전 점검

- [ ] 커밋 제목만 읽어도 무슨 작업인지 알 수 있다.
- [ ] 커밋 하나에 작업이 하나만 들어 있다.
- [ ] 커밋 메시지에 `Co-Authored-By: Claude`, `Claude-Session` 줄이 없다.
- [ ] 새 기준값(임계값, 제외 구간)에는 근거 주석이 있다.
- [ ] 코드를 다시 말하는 주석이나 장식선이 없다.
- [ ] 결과가 바뀌었다면 README 핵심 결과와 해당 case-study 표를 고쳤다.
- [ ] 원본 데이터, 개인정보, 비밀번호가 올라가지 않는다.

### 한 실험이 끝났을 때

1. `case-studies/`에 문서를 쓰거나 기존 문서에 결과를 추가한다.
2. README 실험 목록에 링크와 핵심 질문을 올린다.
3. README 작업 기록 표에 날짜, 한 일, 관련 커밋을 한 줄 추가한다.
4. 막혔던 문제가 있었다면 `docs/troubleshooting.md`에 STAR로 남긴다.
